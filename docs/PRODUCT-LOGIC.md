# Trip Copilot：产品逻辑与设计思考

Trip Autopilot 的目标是减少旅行者从「想去」到「可以出发」之间的劳动：研究、辨别、选择、协调、修改和再次核对。

本文件解释设计选择及其验收方法。当前实现以 [技术架构](ARCHITECTURE.md) 为准，实际通过的范围以 [发布说明](RELEASE-2026-11-18.md) 为准。

## 1. 从用户要完成的事出发

旅行者需要的不只是景点清单。一个方案必须回答：为什么这样选，几件事怎样接起来，哪里还不确定，改变一个条件后应该动哪些地方。

例如，用户说「每天午后休息两小时」，真正的结果应当包含回酒店所需的交通、实际可用的休息窗口，以及对后续活动的调整。摘要中出现「节奏轻松」不算落实。

因此，产品将旅行准备看成一份会持续演进的工作成果：

```mermaid
flowchart LR
    I[想法与约束] --> O[比较与取舍]
    O --> P[可执行的安排]
    P --> D[手册与待办]
    D --> R[新反馈与局部调整]
    R --> P
```

每次交互都应让用户更接近一个可用结果，或者明确一个真正影响结果的决定。

## 2. 供给原子为什么重要

旅行由不同服务组成：景点、交通、住宿、餐饮、当地体验，以及预约规则、价格、时间和条件。将这些内容拆成可组合单元，可以让一次变动定位到相关内容。

供给单元至少需要回答：它是什么、在哪里、适用于什么条件、信息来自哪里、何时核验、还有什么未知。

它不等于真实库存，也不必已经可交易。一条官方票价信息、一段交通规则或一个待核实的候选，都需要保留自己的证据状态。

产品希望在研究、比较、组合和修改之间复用这些资料。复用要保留日期与适用范围：去年某季节成立，不足以证明今年同一天成立；一次被引用，不等于永远有效。

当前实现有供给研究、来源适配、证据缓存和生命周期台账。它们提供基础，但并不意味着统一的全球实时供给网络已建成。

## 3. 个性化是对约束和体验的编排

推荐可以列出「适合亲子」的地点；个性化编排还需要解释具体如何安排、保留什么、放弃什么，以及为何适合这一次出行。

模型需要同时考虑三类信息：

| 信息 | 示例 | 处理原则 |
| --- | --- | --- |
| 明确条件 | 日期、人数、已订酒店、预算上限 | 持续保留；新的明确纠正可以改变旧条件 |
| 偏好与优先级 | 建筑、饮食、慢节奏、核心体验 | 影响选择和取舍，不擅自提升为不可变限制 |
| 暂定假设 | 航班未定时的首末日窗口 | 公开说明可修改，不能冒充用户确认 |

年龄或同行关系不能独自证明偏好、行动能力和消费意愿。用户明确说过的条件与模型提出的合理建议，需要分别保存。

编排质量最终体现在实际时间轴、交通、休息与条件分支中，不能只通过形容词评价。

## 4. 轻量交互：先推进，再问关键问题

连续问卷容易把研究工作推回给用户。产品希望先给出有判断的暂定方案，只在不同答案会实质改变结果时提问。

一个问题应包含三个东西：为什么要问、有哪些容易比较的选择、每个选择会怎样改变方案。

如果不回答也可以推进，就明确临时采用什么假设；如果答案涉及不可代替的授权或关键约束，则不能把沉默视为同意。

代码中意图追问能力允许零到三个问题，并为选项记录方案影响。当前单会话的提示契约也要求少问有用的问题。具体交互是否成功，仍要看真实用户是否能更少操作地得到合适安排。

## 5. 能力模块如何组成产品

产品按用户正在做的决定组织能力，而不是要求每次都机械经过同一套大流程。

| 能力 | 用户正在解决的问题 | 合理产出 |
| --- | --- | --- |
| 比较 | 「这两个方向怎么选？」 | 有取舍依据的选项和需要确认的差异 |
| 意图追问 | 「我还没想清楚要什么。」 | 少量关键问题与可撤回的暂定安排 |
| 供给研究 | 「这个安排有依据吗？」 | 可追溯来源、适用条件、候选与缺口 |
| 局部修订 | 「只改第二天，其他保持。」 | 关联变化、保持项和修改回执 |
| 组装与交付 | 「我到底拿什么去旅行？」 | 可读手册、路线、预算口径、行前待办和导出文件 |

这些模块需要共同理解同一份用户上下文，并明确谁拥有当前计划。否则比较卡选了 A，手册仍写 B；摘要说已改，逐日结构却没变。

当前仓库同时保留能力实验和主路径。比较适配器已明确将「选择」与「实际编辑行程」分开；其他能力也需要逐项说明接入状态，不能用模块清单替代集成证据。

## 6. 为什么采用多个角色

研究、事实裁决和成文关注的内容不同：研究要尽量找到相关信息，裁决要识别证据能支持什么，成文要把可成立的内容组织成好用的旅行安排。

当前首次生成把它们分为三个独立角色会话，按顺序交接。共同资料保存在来源、证据和文档中，而不是仅存在于某个角色的对话记忆里。

这样做希望让证据判断和文章表达有各自的职责边界，但也引入实际摩擦：

- 上一个角色看过的细节，可能没有进入下一个角色的有效上下文。
- 反复发送完整网页和历史，会增加时间、费用并挤压可用上下文。
- 角色完成自己的步骤，不代表最终手册已经保存或满足用户需求。
- 多角色一致同意，也不能证明来源本身正确或适用于当前行程。

实现通过原文持久化、来源索引、逐字证据、明确缺口、定向读取和调用预算控制交接。成文采用可编辑草稿，减少一次性输出完整手册的负担。

这些是对失败机制的工程回应。多角色的价值仍需用相同任务下的质量、延迟、成本和人工接管量来衡量。

## 7. 多语言研究服务于同一个决定

中文内容便于用户理解，目的地当地语言与英文资料可能补充不同的原始信息。研究应围绕关键景点、交通和行动条件展开，按问题选择语言和来源。

输出中文手册时，来源语言可以变化，证据中的实体、日期、条件和不确定性不能丢失。翻译同一篇原文也不会变成新的独立证据。

当前研究规格要求适用时覆盖中文、英文和当地语言，并保留原文及裁决理由。这代表实现意图；项目尚未证明每次运行都充分完成了这一过程。

判断研究是否有效，应查看最终声明实际用了哪些原文、是否匹配本次条件，以及未解决的冲突怎样影响了方案。搜索调用数不能独自回答这些问题。

## 8. 事实校准要影响相关行动

一个看似细小的事实错误，可能改变整天体验。错误的开放时间可能导致空跑，错误的末班衔接可能使返程无法执行。

系统按影响区分事实处理要求：高影响事项需要实际原文支持，缺证时省略确定承诺、保留待确认或提供条件方案；较低影响事项可以带明确不确定性继续交付。

校准还需要把不同状态分开：

| 状态 | 可以表达什么 | 不能推导什么 |
| --- | --- | --- |
| 用户明确输入 | 用户本次这样告诉系统 | 信息已经独立核验 |
| 搜索候选 | 找到可能相关的页面 | 已读全文或已证实声明 |
| 单源原文 | 该来源在这些条件下这样说明 | 已有独立交叉确认 |
| 多源对点 | 匹配同实体、声明、日期与条件的支持 | 未来一定不变或实时库存可用 |
| 建议与估算 | 在所列假设下可考虑的安排 | 已订、已付款或已确认报价 |

来源按声明类型分工，而非简单凑够两个网址：

| 声明类型 | 主要依据 | 对点与限制 |
| --- | --- | --- |
| 价格、营业、预约政策 | 经营者当期官方页面 | 对齐日期、票种、人数与包含项；官方单源仍标未交叉确认 |
| 许可与入境要求 | 相应主管机关 | 明确适用身份及生效期，不把攻略转载当定版 |
| 路线、距离和耗时 | 条件匹配的地图与路线数据 | 区分步行/驾车/公共交通；预计耗时不保证实时结果 |
| 体验与近期现状 | 有时间和场景的游记、评论、公开 UGC | 保留署名、间接性与主观性；同上游转载不算独立 |

核验日期、内容发布日期和出行日期分开。过期资料可以是线索，不能在复用时自动刷新核验时间。S1 是可能空跑、错认实体或破坏关键衔接的高影响事实；S2 带不确定性标注后可交付；S3 不应制造无意义阻断。这是产品政策，程序绑定和模型实际遵守情况仍需分别验证。

对未知的诚实表达应出现在相关安排旁边。文末统一免责声明不能修正正文里错误的确定承诺。

## 9. 手册是产品结果的一部分

旅行者需要在手机上快速理解当天怎么走，也需要一份能带走的完整材料。因此当前交付包括页面手册、完整 PDF 和第一眼速览 PDF。

三者必须围绕同一份正式版本。视觉展示也要有内容责任：正确地点的图片、适当的地图、清楚的日程和预算口径，都是实际可用性的一部分。

下载成功只说明取得文件；不能替代检查缺图、错误实体、截断、旧版本或内容矛盾。模型生成结束、文档保存、产物可下载和整体质量达标需要分别记录。

当前扬州演示在修订、版本保持、刷新和导出上获得限定通过，但购物图片缺失和状态差异仍存在。这些缺口应留在结果说明中。

## 10. 如何衡量进展

项目将以下结果分别衡量，避免用一个总分掩盖不同失败：

| 维度 | 要观察的结果 |
| --- | --- |
| 首次自主交付 | 新行程在没有用户反复救场的情况下，能否形成可用首册 |
| 修订正确性 | 用户要求是否落实，关联内容是否同步，保持项是否真的未变 |
| 修订延迟 | 从提交到可用新版本的真实等待，内部重试和媒体时间都计入 |
| 事实适用性 | 关键声明的实体、日期、人数、条件与来源是否一致 |
| 交付完整性 | 同一版本的页面、图片和两份 PDF 是否达到各自标准 |
| 可恢复性 | 中断或刷新后能否恢复已有有效状态，是否出现重复外部调用 |
| 用户劳动 | 用户花了多少时间补资料、核对、纠正和接管 |
| 成本 | 实际调用与已知用量；估算费用和供应商实付分开 |

离线回归适合验证不变量与失败处理，真实模型运行适合观察判断和工具使用，浏览器与 PDF 复核适合检查实际交付。几类证据相互补充，不能互相替代。

## 11. 当前已知与下一步

最新真实演示从扬州缓存 v2 续改至 v3，验证了限定的修改、保持、刷新和导出链路。它经历内部旧值匹配重试，总等待约 8 分 15 秒，仍有图片和状态差异。

下一阶段应优先验证新单首册、修订等待时间、复杂条件联动和视觉交付完整性。长期记忆、后台跟进、通知和预订执行各自需要授权、状态与失败处理的完整合同。

产品的长期方向是让 Agent 承担更多旅行准备劳动。每一步扩大职责，都应建立在可观测的用户结果之上。
